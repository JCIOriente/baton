# i18n guide

Internationalization and localization for apps used across many countries and languages, on
the client and the server. For storage of instants and collations see `postgres.md`. Project
conventions override this.

## Messages

- **No user-facing text in code.** Every string a user can see (UI, validation errors,
  emails, PDFs, notifications, `aria-label`, `alt`, page titles) comes from a message catalog.
- Keys are stable, semantic and namespaced by feature: `events.list.emptyState`, not
  `noEventsFound` or the English text. Renaming a key is a migration across every locale.
- **Never build sentences by concatenation** or by joining fragments. Word order, gender and
  plural rules differ per language. One message per sentence, with named arguments.
- Use ICU MessageFormat for plurals and selection. Always include `other`. Plural categories
  differ per language (`one`, `few`, `many`, ...), so translators add the ones their language needs:
  ```
  {count, plural, =0 {No attendees} one {# attendee} other {# attendees}}
  {role, select, president {...} other {...}}
  ```
- Arguments are typed values (numbers, dates), not preformatted strings, so the message
  formats them for its locale. Rich text uses tags in the message (`<link>...</link>`), never
  HTML in translations.
- Give translators context: a description per message (where it appears, what each argument
  is, length limits). Don't reuse one key in two places just because the English matches.

## Libraries

- **React (default): FormatJS / `react-intl`.** ICU MessageFormat natively, `Intl`-based
  formatting, and a CLI to extract and compile messages. Alternative: i18next +
  `react-i18next` with the ICU plugin (`i18next-icu`). Without it, i18next uses its own
  plural syntax, so don't mix the two.
- **Rust (default): Fluent (`fluent-rs` / `fluent-bundle`)** for messages, with
  `fluent-langneg` for negotiation. Alternative: **ICU4X** for formatting dates, numbers,
  plural rules and collation, which Fluent alone doesn't cover well. Using both is common.
- Front and back may use different catalog formats. Keep the same locale list, key
  conventions and source-of-truth workflow for both.

## Locales and negotiation

- Identify locales with BCP 47 tags (`es-BO`, `pt-BR`, `fr-CA`, `ar`). Language and region
  are separate concerns: a user in Bolivia may want `en`.
- Resolution order: explicit user preference (stored on the profile) -> locale in the URL or
  session -> `Accept-Language` -> the organization's default -> the app's source locale.
- Fallback chain per message: `es-BO` -> `es` -> source locale. A missing translation shows
  the fallback, never the key, and is reported (log or metric), not silent.
- Load catalogs per locale on demand. Don't bundle every language into the main chunk.

## Translation workflow

- **The source locale is the truth.** Developers add and change messages only there.
  Other locales are produced by translators or a TMS. Don't hand-edit them in feature PRs.
- When the meaning of a source message changes, give it a new key (or mark existing
  translations stale with the tooling). A changed English text with old translations
  is a silent bug.
- CI checks: messages parse as valid ICU/Fluent; every key used in code exists in the source
  catalog; no unused keys; placeholders and tags in each translation match the source.
  Missing translations in non-source locales fail or warn according to the project's policy.
- Adding a language: register the locale, add the catalog, check plural categories, fonts
  and text direction, run pseudo-localization and RTL checks, then have a native speaker review
  the result in context.

## Dates and times

- **Store instants in UTC** (`timestamptz` in Postgres, `Instant`/`Timestamp` in code). Never
  store local times without a zone, and never rely on the server's time zone.
- **Events carry an IANA time zone** (`America/La_Paz`), not an offset. Offsets change with
  DST and law. For future events, the source of truth is local wall time + zone. Derive the
  instant from them, since zone rules can change before the event happens.
- Decide per screen which zone to render in, and label it: the event's zone for "when and
  where it happens" (agenda, certificate), the viewer's zone for "when it happens for me"
  (reminders, countdowns). Show both when they differ and confusion is likely.
- Date-only values (birthdays, deadlines by day) are calendar dates, not midnight UTC.
- Format with locale-aware APIs (`Intl.DateTimeFormat` with `timeZone`; ICU4X on the
  server). Never hand-build formats like `MM/DD/YYYY`. Week start and calendar vary per locale.
- Do zone-aware arithmetic with a zone-aware library (`Temporal` where available or polyfilled,
  `jiff` or `chrono-tz` in Rust). Adding 24 hours is not always "tomorrow".

## Numbers and money

- Format numbers, percentages and units with `Intl.NumberFormat` (or ICU4X). Decimal and
  grouping separators differ per locale. Parse user input locale-aware too.
- Money is an amount + an ISO 4217 currency code. Store integer minor units or a decimal
  type, never floats. Minor units vary per currency (JPY has 0, KWD has 3).
- Display currency according to the viewer's locale, not the currency's country.

## People and places

- Names: don't require first/last names. Use a full or display name plus optional parts.
  Don't uppercase, split or reorder names in code. Allow any Unicode letters and marks.
- Addresses: country-specific shape and required fields. Don't force a postal code or state.
- Phones: store in E.164 and validate or format with libphonenumber (`libphonenumber-js`;
  in Rust, the `phonenumber` crate).
- Countries, languages and currencies are codes (ISO 3166, BCP 47, ISO 4217). Display names
  come from `Intl.DisplayNames` or the catalog, not from a hand-maintained table of names.

## Sorting and search

- Sort user-visible text with locale-aware collation (`Intl.Collator`, ICU4X collator), not
  byte or code-point order. In Postgres, use ICU collations for `ORDER BY` on localized text.
- Search should be case- and accent-insensitive where users expect it (`jose` finds `José`).

## Layout: expansion and RTL

- Design for text expansion of about 40% (more for short labels). Don't use fixed widths for
  text, and don't truncate without a tooltip or another way to see the full text.
- Be RTL-ready from the start: set `lang` and `dir` on `<html>`, use CSS logical properties
  (`margin-inline-start`, `inset-inline-end`, `text-align: start`), mirror directional
  icons, and use `dir="auto"` for user-generated content.
- Don't put text in images. Pick fonts that cover every supported script, or have fallbacks.

## Server-rendered content (emails, PDFs, exports)

- Render in the **recipient's** locale and the document's relevant time zone, not those of
  the request or the server. Store the locale on the user and the document.
- Documents that must stay as issued (certificates, receipts) store the locale and the
  rendered values, or the inputs, so a re-render gives the same text.
- Before choosing a PDF engine, check that it supports complex text shaping and
  bidirectional text (Arabic, Devanagari, Thai) and that it can embed fonts for every script.
- Exports (CSV) are UTF-8. Machine-readable columns use ISO formats. Human-readable reports
  use localized formatting.

## Testing

- **Pseudo-localization** in development and CI (e.g. FormatJS pseudo-locales): accented and
  lengthened text exposes hard-coded strings, concatenation and truncation. Add an RTL
  pseudo-locale or a real RTL locale to the visual checks.
- Per-locale tests of formatted values (dates across zones and DST boundaries, plurals,
  currencies) for a representative set of locales, including at least one RTL locale and one
  with complex plurals (`ar`, `pl`, `ru`).
- Expect ICU/CLDR updates to change output (e.g. narrow no-break spaces in times). Pin the
  runtime's ICU data in CI, and review snapshot changes instead of blindly updating them.
- Test fallback: a locale missing a key renders the fallback, not the key.
